# Оффлайн-развёртывание

Устройства работают без интернета, поэтому образы собираются заранее и едут на
объект одним архивом. Пакет самодостаточен: образы, compose, окружение и
установщик лежат внутри, ничего больше довозить не нужно.

Ролей две, пакеты у них разные:

| Роль | Сервисы | Где ставится |
|---|---|---|
| `master` | `fastapi`, `camera-scanner`, `message-gateway`, `frontend` | одна машина на объект |
| `minion` | `signaling-server`, `storage-service` | каждое устройство с media-center |

Обе роли могут стоять на одной машине — ставятся независимо, друг другу не мешают.

---

## 1. Сборочное устройство

Образы собираются **нативно на arm64** — кросс-сборка через эмуляцию для
`message-gateway` занимает часы. Нужна одна машина `aarch64` с интернетом:

- Docker Engine и плагин `docker compose`
- `git`
- склонированный репозиторий

Проверка:

```bash
uname -m              # должно быть aarch64
docker compose version
```

## 2. Сборка пакета

С ветки, которую собираетесь ставить:

```bash
git pull
chmod +x scripts/build-package.sh          # один раз, бит из Windows не приезжает

./scripts/build-package.sh --role=minion
./scripts/build-package.sh --role=master
```

Флаги:

| Флаг | Значение |
|---|---|
| `--role=master\|minion` | обязательный |
| `--full-auth` | фронт собирается с авторизацией на всех маршрутах, включая `/` и `/kiosk`. Только для `master` |
| `--out-dir=DIR` | куда положить архив, по умолчанию текущий каталог |

На выходе получается, например:

```
varan-master-2026-08-04-70eaa38-auth.tar.gz
varan-minion-2026-08-04-70eaa38.tar.gz
```

Тег версии — дата сборки и короткий git-sha. Если в рабочем дереве есть
незакоммиченные правки или неотслеживаемые файлы, скрипт добавляет `-dirty`
и предупреждает: такой пакет на объект возить не стоит, по нему нельзя
восстановить, что именно собрано.

Внутри архива:

```
images.tar            все образы роли (docker save)
docker-compose.yml    описание сервисов
.env.example          зафиксированные TAG и FULL_AUTH
install.sh
rollback.sh
```

`FULL_AUTH` запекается в образ фронта на сборке и на устройстве **не
переключается** — он отражён в имени пакета и лежит в `.env` только справочно.
Нужны оба варианта — собирайте два пакета.

## 3. Доставка

Архив копируется на устройство любым способом — флешка, `scp`, что угодно:

```bash
scp varan-minion-2026-08-04-70eaa38.tar.gz orangepi@192.168.1.102:~
```

## 4. Установка на устройстве

Docker на устройстве должен быть уже установлен — пакет его не ставит, а только
проверяет наличие и падает с внятной ошибкой, если его нет.

```bash
tar -xzf varan-minion-2026-08-04-70eaa38.tar.gz
cd varan-minion-2026-08-04-70eaa38
sudo ./install.sh
```

Установщик мастера **задаёт вопрос** про корень рабочего каталога, поэтому
терминал должен быть интерактивным. По SSH — только с `-t`:

```bash
ssh -t orangepi@192.168.1.102 'cd varan-master-2026-08-04-70eaa38 && sudo ./install.sh'
```

Без tty скрипт остановится с ошибкой, а не зависнет в ожидании ввода.

### Что спрашивается

```
VARAN_ROOT [/var/lib/varan]:
```

Это корень рабочего каталога varan. В нём лежит `settings/devices.json` —
реестр устройств мастера. Enter принимает значение в скобках; оно берётся
из уже установленного `.env`, а при первой установке — `/home/orangepi/varan`,
если такой каталог есть, иначе `/var/lib/varan`.

Смена корня на уже настроенном устройстве сопровождается предупреждением:
мастер по новому пути увидит пустой список миньонов.

Миньон про корень не спрашивает: `storage-service` работает с фиксированным
`/storage`, а `--varan-root` получает `media-center`, который живёт на хосте.

### Что делает установщик

1. Проверяет `aarch64`, наличие docker, плагина compose, живого демона и права root.
2. Определяет роль по составу `docker-compose.yml`.
3. Спрашивает `VARAN_ROOT` (только мастер) и создаёт `$VARAN_ROOT/settings`.
4. Снимает копию старого стека и удаляет его, если он на устройстве есть — см. раздел 5.
5. Останавливает текущую версию: `docker compose down`.
6. `docker load -i images.tar`.
7. Раскладывает файлы в `/opt/varan-<роль>`, сохраняя прошлый compose как `docker-compose.prev.yml`.
8. Обновляет `/opt/varan-<роль>/.env`: `TAG`, `PREV_TAG`, `COMPOSE_PROJECT_NAME`, `VARAN_ROOT`. Остальные значения существующего `.env` не трогает.
9. `docker compose up -d` и ждёт, пока все сервисы станут `healthy` (до 180 с).
10. Удаляет образы `varan/*` всех версий, кроме текущей и предыдущей.

Каталог распакованного пакета после установки не нужен — состояние живёт
в `/opt/varan-<роль>`.

## 5. Первая установка на устройство со старым стеком

На устройствах, где контейнеры поднимались из репозитория, имена контейнеров
те же самые (`fastapi`, `frontend`, `message-gateway`…), а имена в Docker
глобально уникальны и на проекты не делятся. Плюс все сервисы работают на
`network_mode: host` и держат порты. Поэтому старый стек нужно убрать.

Установщик делает это сам, автоматически и без вопросов — но сначала снимает
копию. Порядок такой:

1. Ищет контейнеры с именами сервисов из нового compose, которые не принадлежат проекту `varan-<роль>`, и печатает их список.
2. Считает, сколько места займёт копия, и сверяет со свободным. Не хватает — установка прекращается до того, как что-либо тронуто.
3. Складывает копию в `/opt/varan-backup/<дата-время>/`:

   | Файл | Что внутри |
   |---|---|
   | `images.tar` | образы старых контейнеров, `docker load -i images.tar` |
   | `containers.json` | `docker inspect`: команды запуска, тома, переменные, порты |
   | `volume-<имя>.tar.gz` | содержимое именованных томов |
   | `README.txt` | краткая памятка по восстановлению |

4. Удаляет старые контейнеры (`docker rm -f`). **Тома при этом не удаляются** и остаются на устройстве.
5. Переносит данные именованных томов в тома нового проекта. Имя тома включает имя проекта, поэтому `rjd_message-gateway-data` без переноса превратился бы в пустой `varan-master_message-gateway-data`, и шлюз потерял бы `gateway-state.json` — таблицу соответствий, сообщения и подключения. Если том нового проекта уже существует, перенос пропускается: содержимое не затирается.

Если копия не помещается на системный раздел, можно указать другой:

```bash
sudo VARAN_BACKUP_DIR=/storage/varan-backup ./install.sh
```

Восстановление автоматическим не делается: контейнеры поднимаются обратно
вручную по параметрам из `containers.json`.

## 6. Обновление

Ровно та же процедура: распаковать новый архив и запустить `sudo ./install.sh`.
Отличия от первой установки:

- в вопросе про корень дефолтом подставляется текущее значение, Enter ничего не меняет;
- прошлая версия остаётся на диске и становится доступной для отката;
- версия старше предыдущей удаляется.

## 7. Откат

```bash
sudo /opt/varan-master/rollback.sh
```

Скрипт меняет местами `TAG` и `PREV_TAG`, откатывает вместе с ними и описание
сервисов, перезапускает и ждёт готовности. Сеть и архив не нужны — образы уже
на устройстве. Перед переключением проверяется, что образы предыдущей версии
действительно есть, иначе скрипт откажется работать.

Повторный запуск возвращает обратно: скрипт переключает две версии между собой.

## 8. Проверка состояния

```bash
cd /opt/varan-master

docker compose ps                    # колонка STATUS покажет healthy
docker compose logs -f fastapi
cat .env | grep -E '^(TAG|PREV_TAG|VARAN_ROOT)='
```

`TAG` в `.env` — единственный достоверный ответ на вопрос «что здесь стоит».

## 9. Что пакет не делает

- **Не ставит Docker.** Он готовится при заливке ОС на устройство.
- **Не ставит `media-center`.** Он собирается своим пайплайном
  ([media-center/scripts/](media-center/scripts/)), работает на хосте, а не в
  докере, и получает `--varan-root` собственным флагом.
- **Не поднимает `can0`.** Интерфейс CAN настраивается на хосте до запуска шлюза.

## 10. Разработка

На машине разработки роли поднимаются из исходников, без пакетов:

```bash
./restart.sh
```

Скрипт перезапускает `media-center` и оба набора контейнеров с явными именами
проектов `varan-master` и `varan-minion`.
