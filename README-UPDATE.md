# Обновление системы

Система обновляется одним файлом на все платы сразу: администратор загружает файл
в «Настройки системы → 02 Обновление системы» и нажимает «Обновить систему».
Платы ничего не скачивают и ничего не собирают — всё нужное лежит в файле.

Версия системы на экране показывается датой и временем сборки выпуска, например
«7 нояб. 2026, 16:16». Внутри это тег `2026-11-07-1616-59abe39`: дата, время и
короткий git-sha коммита.

---

## Термины

| Что | Значение |
|---|---|
| **Выпуск** | Сборка из одного чистого коммита: образы обеих ролей, ядро `media-center` и служба обновления. Тег `ГГГГ-ММ-ДД-ЧЧММ-sha` |
| **Полный файл** | `varan-update-<тег>-full.tar`, все слои образов, ~0,6 ГБ. Нужен для первой установки и для плат старше базы |
| **Дельта** | `varan-update-<тег>-from-<база>.tar`: только слои, которых нет в базе. Изменение кода — единицы-десятки мегабайт, без изменений — 2–3 МБ |
| **Постоянная база** | Выпуск, от которого собираются все дельты. Дельта встаёт на любую плату, где стоит база **или более новый выпуск** |
| **Плата сборки** | `.102`: репозиторий `/home/orangepi/RJD`, манифесты выпусков `~/varan-releases/`, готовые файлы `~/varan-updates/` |

Текущая постоянная база: **`2026-11-07-1616-59abe39`** («7 нояб. 2026, 16:16»).

Что внутри файла обновления:

```
manifest.json            тег, база, части с sha256 и размерами — идёт первым
minion/images.tar.gz     образы signaling-server, storage-service (без слоёв базы)
minion/docker-compose.yml, .env.example, install.sh, rollback.sh
master/images.tar.gz     образы fastapi, frontend, camera-scanner, message-gateway, detection-service
master/docker-compose.yml, .env.example, install.sh, rollback.sh
media-center.deb         ядро: /opt/media-center + юнит media-center.service
updater.deb              служба обновления: update-minion (:8004) и update-master (127.0.0.1:8005)
```

---

## 1. Сборка выпуска

Выполняется на плате сборки (`aarch64`, Docker, `cmake`, `/opt/gstreamer-1.28`, интернет).
На время сборки нужно около 3 ГБ свободного места, после неё остаётся только сам файл.

```bash
cd /home/orangepi/RJD
git pull                                    # ветка, которую ставим

# Дельта от постоянной базы — обычный случай
setsid nohup bash scripts/build-update.sh --out-dir=$HOME/varan-updates \
    > ~/varan-build/build.log 2>&1 < /dev/null &
tail -f ~/varan-build/build.log
```

| Флаг | Значение |
|---|---|
| без флагов | дельта от постоянной базы (`~/varan-releases/BASE`) |
| `--full` | полный файл со всеми слоями |
| `--base=<тег>` | дельта от другого выпуска (нужен его манифест в `~/varan-releases/<тег>/`) |
| `--set-base=<тег>` | сделать выпуск постоянной базой (см. раздел 2) |
| `--full-auth` | фронт с авторизацией на всех маршрутах |
| `--out-dir=DIR` | куда положить файл |
| `--allow-dirty` | собрать из незакоммиченного дерева — **только для отладки**, тег помечается `-dirty` |

Сборщик откажется работать, если в репозитории есть незакоммиченные правки: выпуск
должен однозначно соответствовать коммиту. Ядро собирается Release в отдельном каталоге
`~/varan-build/media-center` в 4 потока (`MC_BUILD_JOBS`), рабочий каталог разработки
`media-center-vscode` не трогается.

В конце печатается, сколько частей изменилось («components changed 3 of 9»), и путь
к файлу. Если дельта больше 200 МБ, будет предупреждение: изменились зависимости или
базовый образ — подумайте о переносе базы.

Забрать файл на ПК:

```bash
scp orangepi-mc:varan-updates/varan-update-<тег>-from-<база>.tar .
```

## 2. Постоянная база

Все дельты собираются от одной базы. Неизменные слои образов одинаковы во всех выпусках
после базы, поэтому дельта подходит и к плате на базе, и к плате на любом более новом
выпуске. Плате **старше** базы нужен полный файл.

Перенести базу на новый выпуск (например, когда дельты разрослись):

```bash
bash scripts/build-update.sh --full --out-dir=$HOME/varan-updates   # собрать новый выпуск
bash scripts/build-update.sh --set-base=<тег нового выпуска>
```

`--set-base` сохраняет образы базы под именем `varan-base/<сервис>:<тег>`: чистка при
обновлениях их не трогает, и следующие сборки берут из них кэш — неизменные слои
собираются байт в байт такими же. После переноса базы все объекты, которые ещё на
старой базе, нужно сначала обновить полным файлом или дельтой нового выпуска,
собранной `--base=<старая база>`.

**Манифесты выпусков `~/varan-releases/` не удалять** — без манифеста базы дельту не
собрать. Копию стоит держать и на ПК.

## 3. Первая установка платы

Делается вручную из **полного** файла. После неё все обновления идут кнопкой.

На плате должны быть: Docker с плагином compose, `/opt/gstreamer-1.28`, `librknnrt`,
сеанс X (`:0`) пользователя `orangepi` — ядро выводит на экран.

```bash
mkdir -p ~/varan-install && tar -xf varan-update-<тег>-full.tar -C ~/varan-install
```

**Флаги ядра.** Файл `/etc/default/media-center` хранит флаги этой платы. Если на плате
был юнит `/etc/systemd/system/media-center.service`, установщик сам перенесёт флаги из
него. Если юнита нет или он старый, задайте файл заранее:

```bash
sudo tee /etc/default/media-center <<'EOF'
MC_ARGS="--rest-port=7777 --signaling-ip=127.0.0.1 --signaling-port=8765 --varan-root=/var/lib/varan --modules=birdview,neural --gateway-ip=<IP мастера> --gateway-port=50051 --detection-ip=<IP мастера> --detection-port=50052"
EOF
```

`--detection-ip` — адрес мастера. По нему служба обновления платы принимает команды
**только от мастера**. На самом мастере это `127.0.0.1`.

**Каждая плата** (роль исполнителя: сигналинг, хранилище, ядро, служба обновления):

```bash
cd ~/varan-install/minion && sudo ./install.sh
```

**Плата мастера** — дополнительно роль мастера. Установщик спросит корень данных
мастера `VARAN_ROOT` (там `settings/config.db` с профилями и `devices.json`), поэтому
по SSH — только с `-t`:

```bash
cd ~/varan-install/master && sudo ./install.sh
```

Проверка:

```bash
systemctl is-active media-center update-minion        # на всех платах
systemctl is-active update-master                     # на мастере
curl -s http://127.0.0.1:8004/status                  # версии ролей платы
```

Затем добавьте плату на мастере в «Устройства» — служба обновления берёт список плат
из реестра устройств.

Если на плате ядро запускалось вручную (tmux, `mc-deploy-run`), остановите его до
установки: пакетное ядро занимает порт 7777 и перезапускается systemd само.

## 4. Обновление по кнопке

1. «Настройки системы → 02 Обновление системы» (только администратор).
2. «Выбрать файл» или перетащить файл в панель справа. Файл проверяется по sha256.
3. Справа появится «Выпуск <дата, время>», что изменилось и список проверок. Красные
   проверки блокируют запуск — см. раздел 6.
4. «Обновить систему» → подтверждение.

Что происходит:

| Этап | Что делается | Видео и запись |
|---|---|---|
| Доставка | части файла уходят на все платы параллельно; образы загружаются рядом с работающими, ядро проверяется во временном каталоге | работают |
| Установка | на каждой плате: остановка ядра и контейнеров исполнителя, установка, запуск, проверка | пропадают |
| Часть мастера | перезапуск FastAPI, фронта, шлюза, сервиса обнаружений. Экран покажет «Мастер перезапускает свои службы» — это нормально | — |
| Проверка | контейнеры healthy, ядро отвечает, конфигурация мастера применена (камеры, нейросети и 360 не учитываются) | возвращаются |

Простой — 1–3 минуты. На каждом экране, пока идёт обновление, в верхней панели видна
плашка «Обновление: …». Мастер в это время отвечает отказом на любые изменения
конфигурации («System update is running»).

«Отменить обновление» доступна только во время доставки: доставленные файлы
удаляются, на платах ничего не меняется.

После успеха файл убирается, служба обновления на платах обновляет сама себя.

## 5. Если обновление не прошло

**Любой сбой на любой плате возвращает все платы на прежнюю версию.** Экран покажет
красный баннер с причиной и кнопкой «Журнал платы».

| Сообщение | Что значит | Что делать |
|---|---|---|
| не поднялись контейнеры за 3 мин: … | контейнер не стал healthy | `docker logs <контейнер>` на плате |
| ядро не ответило за 3 мин | `media-center` не ответил на `/system/info` | `journalctl -u media-center -n 100`, флаги в `/etc/default/media-center` |
| конфигурация не применена: … | плата не приняла пакет конфигурации мастера | экран «Конфигурации» → «Применение» |
| связь пропала во время установки | плата перестала отвечать | плата вернётся на прежнюю версию **сама**, как только появится в сети |
| плата отказала: Commands are accepted only from the master | `--detection-ip` платы не совпадает с адресом мастера | исправить `/etc/default/media-center` |
| install.sh … завершился с кодом N | ошибка установщика | «Журнал платы» — там полный вывод |
| Доставка не удалась, на платах ничего не изменилось | файл не дошёл или не подготовился | чаще всего не хватает слоёв: нужен полный файл |

Файл после отката остаётся загруженным — после исправления нажмите «Повторить».

Журналы на плате:

```bash
journalctl -u update-minion -u update-master -n 200    # служба обновления
sudo cat /var/lib/varan-updater/board.log              # журнал последней операции платы
sudo cat /var/lib/varan-updater/rollout.json           # последний ход обновления (мастер)
```

Ручной откат одной платы (если служба обновления недоступна):

```bash
sudo /opt/varan-minion/rollback.sh --to=<тег>     # и /opt/varan-master/rollback.sh на мастере
```

`--to` ставит плату ровно на указанную версию: если она уже текущая — только поднимает
сервисы, если предыдущая — переключает. Ядро возвращается из сохранённых пакетов
`/opt/varan-minion/debs/`.

## 6. Если система не даёт запустить обновление

Перед запуском экран показывает проверки. Красные запрещают запуск, жёлтые требуют
внимания, серые — пропущенные платы.

| Проверка | Почему | Что делать |
|---|---|---|
| **Дельта не подходит к этой системе** | на плате версия старше базы, от которой собрана дельта | загрузить **полный** файл |
| **«Плата» без службы обновления** | на плате нет `update-minion` (старая установка) или служба остановлена | поставить плату вручную из полного файла (раздел 3) или `sudo systemctl start update-minion` |
| **Идёт смена профиля** | мастер переключает профиль | дождаться конца смены или завершить её на экране «Конфигурации» |
| **Мастер не отвечает** | FastAPI недоступен | `docker ps`, `docker logs fastapi` на мастере |
| **Плата мастера не найдена** | в реестре устройств нет платы с ролью мастера или на ней нет службы обновления | добавить плату мастера в «Устройства», проверить `update-minion` на ней |
| **«Плата» занята** | на плате ещё идёт операция обновления или возврат пропавшей платы | подождать |
| Нужно N ГБ на «Плата» (жёлтая) | места меньше, чем займут файл и образы | можно запускать: очистка архива удалит самые старые записи по своим правилам |
| Файл не новее установленной версии (жёлтая) | загружен тот же или более старый выпуск | запуск попросит подтверждения |
| «Плата» офлайн, будет пропущена (серая) | плата не отвечает | обновится позже тем же файлом, пока он подходит |

Отказы при загрузке файла:

| Сообщение | Что делать |
|---|---|
| Not a valid update file / manifest.json must be the first entry | файл повреждён или не тот — скопировать заново |
| Part …: sha256 mismatch | файл повреждён при копировании — скопировать заново |
| Not enough disk space | освободить место на мастере |
| An update is running | дождаться конца текущего обновления |

## 7. Вернуть предыдущую версию

Кнопка «Вернуть предыдущую версию» (когда файл не загружен) ставит все платы на
предыдущий выпуск тем же путём, с проверкой и общим откатом при сбое. Файл не нужен:
прежние образы и пакет ядра лежат на платах. Повторное нажатие возвращает обратно.

Платы хранят ровно две версии — текущую и предыдущую. После неудачного обновления
и общего отката «предыдущей» становится версия, которая не встала: более старые образы
к этому моменту уже удалены. Служба обновления сама при возврате не откатывается.

## 8. Ограничения

- Одна база на файл; плате старше базы нужен полный файл.
- Платы офлайн пропускаются и остаются на своей версии.
- Истории обновлений нет: на экране только последний ход, полная история — в `journalctl`.
- Подписи файла нет: целостность — sha256 каждой части, право запуска — роль администратора.
- Обновление не меняет флаги ядра: они в `/etc/default/media-center` на каждой плате,
  после правки — `sudo systemctl restart media-center`.

## 9. Плата разработки .102

С 7 ноября 2026 `.102` работает в стандартной раскладке: `/opt/varan-*`, ядро —
`systemd` (`media-center.service`, `Restart=always`), корень данных мастера
`/var/lib/varan`, корень ядра `/home/orangepi/varan`. Запуск ядра в tmux
(`mc-deploy-run`) и `rjd-pull-compose` с ней конфликтуют.

Вернуть отладочную раскладку:

```bash
sudo systemctl disable --now media-center     # освободить порт 7777 для ядра в tmux
# контейнеры из репозитория — задачей rjd-pull-compose
```

Вернуться к стандартной: собрать выпуск, поставить его кнопкой или вручную
(`install.sh` обеих ролей), `sudo systemctl enable --now media-center`.
