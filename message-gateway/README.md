# message-gateway

Отдельный сервис-шлюз обмена сообщениями. media-center отдаёт **семантику**
(кадр: изображение + детекции + мета + версия протокола) по gRPC, шлюз проверяет
поддержку версии, кодирует под конкретный протокол и отправляет стороннему
клиенту. Реализованы три канала: **WebSocket** (кадр с изображением в КАУС),
**CAN** (обнаружения на шину изделия по J1939) и **Modbus RTU** (записи
обнаружений для АС КРСПС, конфигурация «Искра»). Новые каналы добавляются
новым модулем без изменения остального кода.

Смысл слоя — развязка: при смене wire-формата протокола правится кодек в шлюзе,
ядро C++ не трогается и не пересобирается.

Два интерфейса:
- **gRPC (порт 50051)** — ingress кадров. Высокочастотный путь с изображением,
  поэтому gRPC (потоковый), а не HTTP.
- **REST (порт 9090)** — настроечные ручки. Их дёргает веб-страница по запросу.

## Сборка

Все зависимости ставятся в контейнере apt-ом, CMake подбирает их через
`find_package`. Отдельно вендорить ничего не нужно.

```
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
```

Нужны (в образе уже прописаны в Dockerfile): C++20, `libboost-dev`,
`libboost-json-dev`, `protobuf-compiler`, `protobuf-compiler-grpc`,
`libprotobuf-dev`, `libgrpc++-dev`. Сборка идёт под Linux (контейнер).

## Запуск

```
./message-gateway --rest-port 9090 --grpc-port 50051 \
    --ws-host 192.168.1.50 --ws-port 8080 --ws-target /ws/frames --heartbeat 5 \
    --can-mode socketcan --can-iface can0 --can-src 0x71 --can-peer 0x61
```

Режим slcan (USB-адаптер на serial port), внешний `slcand` не нужен:

```
./message-gateway --can-mode slcan --can-device /dev/ttyUSB0 --can-bitrate 250000
```

Все параметры опциональны; дальше всё настраивается в рантайме через REST.
WebSocket-клиент к КАУС переподключается бесконечно (каждые 10 с), шина — каждые
5 с, даже если попытки неуспешны.

Флаги CAN: `--can-mode` (`socketcan`/`slcan`), `--can-iface`, `--can-device`,
`--can-bitrate`, `--can-src` (наш адрес), `--can-peer` (адрес Садко),
`--can-enabled 0`. Адреса принимают и `0x71`, и `113`.

`--backend-url` (по умолчанию `http://127.0.0.1:8000`) — бэкенд мастера, у
которого «Искра» раз в 5 с спрашивает `/api/neural/status` для регистра
состояния Modbus. Порт и адреса Modbus настраиваются только по REST.

## gRPC ingress кадров

Контракт — [proto/frame-ingress.proto](proto/frame-ingress.proto):

```proto
service FrameIngress {
    rpc StreamFrames(stream FrameRequest) returns (stream FrameReply); // видеопоток
    rpc SendFrame(FrameRequest) returns (FrameReply);                  // одиночный
}
```

`FrameRequest` — семантическая модель (не wire-формат): `ver`, `id`, `ts`,
`width/height/format`, повторяемые `dets` и `image` (сырые байты, поле `bytes`).

Для видеопотока media-center открывает **один** `StreamFrames` и шлёт кадры
подряд, получая `FrameReply` на каждый. Кадр раздаётся всем модулям активной
конфигурации, их ответы сводятся в один:
- взял хотя бы один модуль → `accepted:true, transport:"websocket+can",
  wire_size:...` (сумма по взявшим);
- не взял никто → `accepted:false`, в `error` причины по модулям через `;`,
  напр. `websocket: websocket not connected; can: can bus not connected`
  (кадры не буферизуются, чтобы очередь не росла);
- все модули не знают версию → `accepted:false,
  error:"unsupported ... (supported: 1)"`, поток не рвётся.

Кодек v1 (модуль WebSocket) собирает wire-кадр протокола: `[uint32 BE длина JSON]
[JSON-заголовок][image bytes]`, шлёт бинарным WS-фреймом. При простое канала шлюз
сам шлёт heartbeat каждые `heartbeat_sec` секунд. Модуль CAN версию протокола
изображения не смотрит: у него свой кодек и своя раскладка (см. ниже).

## Интеграции (конфигурации) и модули

Два уровня. **Интеграция** (`IIntegration`, [integration.h](include/gateway/integration.h)) —
конфигурация целиком; активна одновременно одна, выбор по REST
(`POST /integrations/select`). **Модуль** (`IModule`, [module.h](include/gateway/module.h)) —
один канал доставки внутри неё: свой транспорт, настройки, соединение и
статистика.

Реализованы две интеграции. **РСМ-2000** (`rsm-2000`, активна по умолчанию) с
двумя модулями:

| Модуль | Что делает |
|--------|------------|
| `websocket` | кадр (изображение + обнаружения) в КАУС по протоколу v1 + heartbeat |
| `can` | обнаружения на шину изделия (J1939) + приём времени и GPS от Садко |

Кадр из ingress уходит в **оба** модуля: это независимые каналы, молчание одного
не мешает другому. Ответ ingress'у сводится так: взял хотя бы один — `accepted`.

**Искра** (`iskra`) — один модуль `modbus`: записи обнаружений для АС КРСПС по
Modbus RTU и время с GPS от АС КРСПС (см. раздел ниже).

Новый канал = новая реализация `IModule` и `push_back` в конструкторе интеграции;
новая конфигурация = новая реализация `IIntegration` и `push_back` в
`setup_integrations()`. Ядро не меняется. Страница КРСПС рисует каждый модуль
отдельным разделом в левом столбце.

## Таблица соответствий

Шлюз получает от мастера обнаружений **только числа** и не знает их смысла.
Таблицу соответствий и словари протоколов хранит и применяет мастер: они
настраиваются на экране «Конфигурации» в разделах «Таблица соответствий» и
«Словари», свои у каждой конфигурации шлюза. Числа приходят в `FrameRequest`:
`dets[].type`, `dets[].danger`, `camera_no` для CAN и `record` для Modbus.
`0` везде значит «пусто». Названия чисел страница берёт из словарей мастера;
поле записи Modbus указывает ключ словаря в `dict` (`code`, `cameras`, `zone`).

## Модуль CAN

Шина за интерфейсом `ICanBus` ([can-bus.h](include/gateway/can-bus.h)), две
реализации, режим переключается настройкой `mode`:

| Режим | Чем является | Настройки |
|-------|--------------|-----------|
| `socketcan` | raw-сокет Linux на интерфейсе (штатный путь) | `iface` (`can0`) |
| `slcan` | USB-адаптер прямо на serial port, ASCII-протокол Lawicel | `device`, `bitrate` |

Список того, что есть на машине, отдаёт `GET /devices` — страница показывает его
подсказкой к полю, чтобы имя не вбивали наугад. В контейнере это работает за счёт
`privileged: true` и монтажа `/dev:/dev` (см. `docker-compose.yml`): перечислять
устройства через `devices:` нельзя — тот список проверяется при старте, и
контейнер не поднялся бы, пока адаптер не воткнут. Сервис же обязан стартовать на
машине без железа и ждать.

В режиме `socketcan` скорость шины задаётся **снаружи** — сокет её не выставляет:

```
ip link set can0 up type can bitrate 250000
```

В режиме `slcan` шлюз сам открывает порт (115200 8N1) и гоняет `C` → `S<n>` → `O`;
скорость берётся из `bitrate` (допустимы значения ряда S0..S8: 10000…1000000).
Внешний `slcand` при этом не нужен. Шина переподключается бесконечно (каждые 5 с).

### Передача: обнаружения (наше сообщение)

Приоритет `0`, PGN `0xEF00`, SA `0x71` → 29-битный id **`0x00EF0071`**. Кадр
уходит **строго по таймеру** раз в `tx_period_ms` (по умолчанию 100 мс)
**независимо от gRPC**: сообщения мастера только обновляют нагрузку. Так
период на шине ровный и не зависит от частоты работы нейросети.

| Байт | Значение |
|------|----------|
| 1 | количество живых обнаружений в списке |
| 2 | тип обнаружения (у обнаружения с наивысшим классом опасности) |
| 3 | класс опасности |
| 4 | номер камеры того же обнаружения |

Нагрузка — **список обнаружений мастера по ID**: «Подтверждён» без картинки
добавляет (повтор ID не дублирует), «Удалён» вычитает; сообщения с картинкой
(они для ЦПУ) и остальные события пропускаются. Тип, опасность и номер камеры
берутся у самого опасного живого обнаружения (при равной опасности — у раннего);
обнаружений нет — кадр `00 00 00 00`. Смена сессии мастера (`session` в
сообщении) очищает список.

Протокол задаёт 4 значащих байта, но J1939 требует в кадре все 8, поэтому по
умолчанию `tx_dlc = 8`, а хвост заполняется `0xFF` («значение недоступно»). Если
приёмник ждёт ровно 4 — поставьте `tx_dlc = 4`.

Жизнь нагрузки (`payload_ttl_enabled`) включена — обнаружение гаснет через
`payload_ttl_ms` (по умолчанию 1 с) после «Подтверждён» и до «Удалён» остаётся
в списке погашенным: повторный «Подтверждён» его не оживляет. Выключена —
обнаружение держится до «Удалён» или смены сессии мастера.

Тумблер `tx_continuous` выключает выдачу по таймеру: тогда кадр уходит только
при изменении нагрузки (в том числе при погасании по сроку).

### Приём: время и GPS (сообщения Садко)

Слушаются сообщения устройства с адресом `peer_addr` (`0x61`), период 0,5 с:

| Сообщение | id | Что несёт |
|-----------|-----|-----------|
| координаты | `0x18FF0061` (PGN `0xFF00`) | широта/долгота: градусы, минуты (биты 1–6), знак (биты 7–8), секунды ×1000 (uint16 LE) |
| дата и время | `0x18FF0161` (PGN `0xFF01`) | год/месяц/день/час/минута/секунда UTC + путевая скорость (uint16 LE, 0,01 м/с) |

Принятое уходит в `UTimeSource`, откуда время и GPS забирают остальные сервисы
(REST `/time`, gRPC `GetTime`). Пока по шине ничего не пришло, отдаются часы
сервиса и заглушка координат: `source.time = "ntp"`, если ядро считает часы
выверенными по NTP (как `timedatectl`), иначе `"server"`; в gRPC это `ntp_time`.

**Время от шины используется исключительно**, но хранится не «как есть»: оно
приходит с точностью до секунды раз в 0,5 с, и между сообщениями стояло бы на
месте — два кадра подряд получили бы одну метку. Поэтому запоминается момент
приёма по монотонным часам, а при выдаче добавляется натикавшее с тех пор:
время остаётся временем Садко, но идёт непрерывно. Системные часы контейнера
не трогаются (не нужен `CAP_SYS_TIME`). Источник пропал — время идёт от
последнего значения, на часы платы не переключается.

Новое значение принимается как есть, даже если расходится с ожидаемым (прежнее
плюс натикавшее). Расхождение больше 2 с (`TIME_JUMP_MS`) модуль пишет в лог
предупреждением: величина, новое и ожидаемое время UTC и сырые данные — байты
кадра и раскладка у CAN, регистры `0x2008–0x200B` у Modbus.

Координаты считаются достоверными (`gps.valid`), только пока сообщения идут:
двухсекундная тишина при периоде 0,5 с — это уже потеря связи.

## Модуль Modbus (Искра)

Три слоя, общие для всех систем на Modbus, и реализация конфигурации поверх:

- `AModbusModule` (`modules/modbus/module`) — ведомый Modbus RTU на serial port
  (USB–RS485). Свой RTU на `boost::asio::serial_port`, без libmodbus: функции
  `0x04`, `0x06`, `0x10`, CRC16 и длина кадра по коду функции (`rtu`), мусор и
  неверный CRC пропускаются сдвигом на байт, ответы чужих ведомых на общей шине
  узнаются и не считаются ошибками. Остальные функции — исключение `01`, неверное
  число регистров — `03`. Широковещательная запись (адрес 0) исполняется без
  ответа. Содержимое регистров задаёт наследник (`read_input`, `write_holding`).
- `AKrspsModule` (`modules/modbus/krsps`) — протокол АС КРСПС v2.3: блок
  состояния, окно записей, отметка, время и GPS ведущего, очередь записей
  (`queue`), скрытие записей до первого времени. Конфигурация задаёт пакеты,
  регистры состояния, прочие команды, настройки `0x8000` и что делать со временем
  и GPS ведущего.
- `AModbusPacket` (`modules/modbus/packet.h`) — кодек пакета: длина, время в
  регистрах записи, описание полей для страницы. Тело записи собирает
  конкретный кодек из данных своей конфигурации.
- Искра (`core/iskra-integration`): `UIskraPacket28163`, `UIskraModbusModule`
  (записи из поля `record` сообщений мастера, регистр `0x1007`, время и GPS в
  `UTimeSource`) и `UIskraIntegration` (модуль + опрос техзрения).

По умолчанию: `/dev/ttyUSB0`, 115200 8N1, адрес 20; порт переоткрывается каждые 5 с.

| Регистры | Что лежит |
|----------|-----------|
| Input `0x1000–0x1005` | идентификатор (20), версия (1), длина записи (одна у всех пакетов конфигурации и у всех записей очереди, иначе 0; у Искры 32), `0x1000` регистров окна, 3 регистра команд, число регистров состояния |
| Input `0x1006` | видимых записей; при `limit_records` (по умолчанию) не больше `max_records` (1023) — обход ведущего, теряющего старшие биты; записи остаются в очереди и вычитываются порциями |
| Input `0x1007…` | регистры состояния конфигурации; у Искры один: 1 — все слоты техзрения плат запущены и все плитки камер `ok` |
| Input `0x2000–0x2FFF` | окно: видимые записи с головы подряд, сколько целиком помещается; хвост — нули |
| Holding `0x1000–0x1002` | команда `0x0001` «отметка прочитанных» и номера первой и последней; прочие команды — конфигурации, по умолчанию `03` |
| Holding `0x2000–0x200B` | координаты и время UTC от АС КРСПС |
| Holding `0x8000–0x8008` | настройки порта от АС КРСПС — конфигурации, по умолчанию `02` |

Адреса вне `0x1000–0x2FFF` и настроек — исключение `02`.

**Записи** создаёт конфигурация: у Искры — только из сообщений мастера с полем
`record` (пакет 28163: длина, номер, тип 1, время, координаты, код, ID
стоп-кадра, маска камер, зона, число объектов). Номера 0–65535 по кругу, первая
запись после пустой очереди — №1; отметка снимает записи с головы, только если
номера совпали с записями окна. Очередь — до 65 535 записей, при переполнении
выбрасывается старейшая. Каждое изменение пишется фоновым потоком в
`modbus-queue.bin` рядом с файлом настроек (временный файл, fsync, rename) и
поднимается при старте. Формат `MBQ2`: номер, скрыта, время, пакет, регистры
записи; файл другого формата уходит в `.corrupt`.

**Время.** Пока в этом запуске от АС КРСПС не пришло время, новые записи скрыты
(`0x1006` их не считает). Первое время открывает их со сдвигом на разницу
времени АС КРСПС и часов платы, кодек переписывает время в регистрах. Искра
кладёт время и GPS в `UTimeSource` с источником `modbus`; координаты достоверны
15 с. Буквы полушарий принимаются в любом из регистров `0x2006`/`0x2007`.
Координаты записи Искры — из сообщения, а без них — от АС КРСПС на момент приёма.

**Регистр состояния** Искры считает интеграция: раз в 5 с `GET /api/neural/status`
бэкенда; 0 и причина (`device_offline`, `no_module`, `no_slots`, `slot_stopped`,
`no_tiles`, `tile_fault`, `no_devices`, `backend_unavailable`) уходят в статус
модуля кодом и текстом для страницы.

**Лог кадров** (`[modbus:frame]`, всегда): строка на каждый кадр линии —
направление, адрес, функция в hex, разбор и все байты через пробел. Запросы к
нам и чужим адресам (`foreign`), ответы чужих ведомых, широковещательные
(`broadcast`), наши ответы (`TX`); отклонённое — WARN: неверный CRC (принятые
и посчитанные байты CRC), мусор одной строкой до следующего кадра, исключения.
Значения регистров в ответе — до 8 регистров. Поэтому ротация лога шлюза в
compose — 5 × 50 МБ.

```
INFO  [modbus:frame] RX 19 04 read 0x1006x2 | 13 04 10 06 00 02 96 78
INFO  [modbus:frame] TX 19 04 response 4 bytes: 1023 1 | 13 04 04 03 FF 00 01 …
WARN  [modbus:frame] TX 19 91 exception 01 (illegal function) | 13 91 01 2C 55
INFO  [modbus:frame] RX 18 04 foreign read 0x1000x62 | 12 04 10 00 00 3E 75 2A
WARN  [modbus:frame] RX bad CRC: 19 04 read 0x1006x2, CRC 12 34 instead of 96 78 | 13 04 10 06 00 02 12 34
WARN  [modbus:frame] RX garbage 3 bytes | FF 00 13
```

Статус модуля (`/status`, `modules[0]`): `connection` (порт, скорость,
чётность, фаза переподключения), `slave`, `master` (на связи, если запросы шли
за последние 15 с), `slave` (адрес, идентификатор, версия, `limit_records`, `max_records`), `block` (значения `0x1000–0x1006`; `0x1006` — отправленное ведущему, настоящее — `queue.visible`), `state.registers`
(адрес, значение, подпись, норма, код и текст причины), `time`, `gps`, `queue`
(всего, видимых, скрытых, в окне, выброшено, следующий номер, последняя
отметка, последние 20 записей со статусом `hidden|queued|read|dropped`, `head` —
запись в начале окна или `null`; у записи — номер, пакет, время UTC, регистры и
поля от кодека), `counters` (запросы, широковещательные, исключения, CRC,
мусорные байты, чужие запросы и последний чужой адрес, отметки), `log`
(последние 100 обменов: функция, регистры, вид, байты запроса и ответа).

Проверка без железа — стенд `testing/krsps-modbus` (ведущий на pty).

## REST API (настройка)

| Метод | Путь | Назначение |
|-------|------|------------|
| GET  | `/health` | статус сервиса, соединение с КАУС, id активной интеграции |
| GET  | `/integrations` | список конфигураций + активная |
| POST | `/integrations/select` | выбрать активную конфигурацию `{ "id": "rsm-2000" }` |
| GET  | `/status` | полный статус активной: соединение + счётчики + последние сообщения |
| GET  | `/config` | конфигурация активной интеграции |
| PUT  | `/config/websocket` | обновить host/port/target/enabled/heartbeat_sec и переподключиться |
| PUT  | `/config/can` | обновить mode/iface/device/bitrate, адреса сообщений, период; шина переподнимается только при смене того, что её определяет |
| PUT  | `/config/modbus` | обновить device/baud/parity/data_bits/stop_bits/enabled (порт переоткрывается) и slave/device_id/version/limit_records/max_records (1–65535) |
| GET  | `/devices` | интерфейсы CAN и serial-порты, которые видит сервис |
| POST | `/modules/connect` | поднять модуль: `{ "module": "can" }` |
| POST | `/modules/disconnect` | погасить модуль: `{ "module": "can" }` |
| POST | `/ws/connect` | поднять активную интеграцию целиком (все модули) |
| POST | `/ws/disconnect` | погасить активную интеграцию целиком |
| GET  | `/ws/status` | состояние соединения активной интеграции |
| GET  | `/protocol/versions` | поддерживаемые версии сообщений |
| GET  | `/time` (`/gps`) | точка входа времени и GPS для остальных сервисов |

Наружу REST проксируется nginx под `/api/gateway/*`. gRPC-ingress внутренний
(media-center → localhost:50051), через nginx не публикуется.

### PUT /config/websocket

Частичное обновление, тело JSON:

```json
{ "host": "192.168.1.50", "port": "8080", "target": "/ws/frames", "enabled": true, "heartbeat_sec": 5 }
```

### PUT /config/can

Частичное обновление, тело JSON. Состав полей сообщения задан протоколом и в
настройках не живёт — меняется только адрес, из которого собирается id, и
разбор/отправка сообщения целиком (`enabled`). Смена `mode`/`device`/`bitrate`/
`iface`/`enabled` переподнимает шину; правка PGN живое соединение не роняет.

```json
{
  "mode": "socketcan", "iface": "can0", "enabled": true,
  "tx_detections": { "priority": 0, "pgn": 61184, "addr": 113, "enabled": true },
  "tx_continuous": true, "tx_period_ms": 100, "tx_dlc": 8, "payload_ttl_ms": 1000,
  "rx_gps":  { "priority": 6, "pgn": 65280, "addr": 97, "enabled": true },
  "rx_time": { "priority": 6, "pgn": 65281, "addr": 97, "enabled": true }
}
```

### GET /devices

Что сервис видит на машине. Пустые списки — не ошибка: сервис обязан подниматься
без железа и подхватывать адаптер по факту появления.

```json
{
  "can":    [ { "name": "can0", "up": true, "kind": "can" } ],
  "serial": [ { "name": "/dev/ttyUSB0" } ]
}
```

### GET /time

Время и GPS от Садко с шины CAN. Общая точка входа для остальных сервисов.
Пока по шине ничего не пришло — часы сервиса и заглушка координат
(`source.time = "ntp"` у выверенных по NTP часов, иначе `"server"`; `source.gps = "static"`).

```json
{
  "unix_ms": 1718700000000, "unix_s": 1718700000, "iso": "2024-06-18T08:00:00Z",
  "gps": { "lat": 55.7695, "lon": 37.6626, "alt": 0.0, "valid": true,
           "sats": 0, "speed": 1.0, "course": 0.0, "age_ms": 120 },
  "source": { "time": "can", "gps": "can" }
}
```

`alt`/`sats`/`course` нулевые: Садко их не передаёт. `age_ms` — сколько прошло с
последнего сообщения координат.

## Замечания

- ingress держим **семантическим**. Если начнёте гонять через шлюз уже собранные
  wire-кадры «как есть» — слой становится чистым проксированием, тогда дешевле
  слать из media-center напрямую.
- при отсутствии соединения кадры не буферизуются, чтобы очередь отправки не
  росла бесконтрольно.
