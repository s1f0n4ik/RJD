# Испытательный стенд RJD

Отдельное приложение FastAPI для машины, на которой работает RJD. В одном контейнере находятся веб-интерфейс, API, исполнители проверок, эмуляторы CAN/Modbus/WS, Chromium и источник эталонного RTSP. Другие контейнеры стенд не создаёт. Существующим MC и контейнерами приложения он управляет через SSH на эту же машину.

## Запуск

Перед сборкой и загрузкой образа проверьте логический запас до очистки архива: физическое свободное место не учитывает резерв журнала. Сам образ и Docker build cache тоже занимают общий диск. Не выполняйте сборку на машине приложения, если её записи могут пересечь порог очистки.

Задайте переменную окружения `TEST_PASSWORD` — пароль оператора от 12 символов. Из корня репозитория:

```sh
docker compose -f testing/test-service/compose.yaml up -d --build
```

Интерфейс: `http://<адрес-машины>:8088`. Порт меняется через `TEST_PORT`. Compose содержит один сервис. Именованный том `rjd-testing_testing-data` хранит настройки подключения, SSH-ключ, незавершённую сессию, отчёты, доказательства и библиотеку видео. Не удаляйте этот том при обновлении. Обычный перезапуск стенда не запускает новые испытания.

Образ собирается для архитектуры машины сборки; для Orange Pi нужен `linux/arm64`. Сборка требует доступа к пакетным репозиториям, работа готового образа — нет. Образ можно передать на закрытую машину через `docker save` / `docker load`.

## Подключение

1. Войдите паролем оператора и откройте «Подключение».
2. Укажите локальные адреса сервисов, точный путь исполняемого файла MC и рабочий каталог. Если MC работает, стенд сохраняет его реальные аргументы и окружение для восстановления. Если выключен — используется настроенная команда запуска.
3. Укажите SSH-пользователя и загрузите незашифрованный приватный ключ. Ключ хранится в закрытом каталоге тома и не включается в отчёты.
4. Укажите SHA256-отпечаток ключа SSH-хоста, проверенный по доверенному каналу. Подключение с отсутствующим или несовпавшим отпечатком отклоняется.
5. Пользователь SSH должен читать метрики и архив, управлять своим MC и иметь доступ к Docker приложения. Для создания vcan нужны права NET_ADMIN и модуль ядра. Вариант `sudo -n` требует предварительно настроенного доступа без интерактивного запроса пароля.
6. В «Испытаниях» выберите блоки и выполните предварительную проверку. Она не начинает нагрузку. Отдельная кнопка запускает испытания.

Стенд проверяет, что привязки профиля относятся к одному локальному устройству. Подключение работающего API MC при несовпадающем пути процесса блокирует запуск.

## Испытания и восстановление

Одновременно возможна одна сессия: выбранные/полные испытания либо постоянная эмуляция. Нагрузка по умолчанию длится 60 минут; финальная сверка, протокольные сценарии и восстановление могут увеличить общую длительность. Число потоков, повторения, сценарий и список перезапусков задаются перед стартом.

Автотест создаёт временный профиль **настроек** с прежними путями данных. Он проверяет доступность и ревизии сервисов, открытие/закрытие WebRTC, слоты и конфигурации, пресеты/поток 360, запись и индекс, протоколы, эталонный сценарий и поочерёдные перезапуски. Протокольные контрольные сообщения идут в настоящий шлюз, но обходят MC и обнаружения; этот участок явно отделён от сквозной проверки.

**Данные приложения текущие.** Новые MP4, записи журнала и изменения очередей остаются. Автотест Modbus может подтверждать записи, принятые до начала испытания; отчёт содержит количество и известные идентификаторы таких подтверждений. Восстановление настроек не возвращает подтверждённую очередь.

После успеха, отмены или ошибки возвращаются исходный профиль и первоначальное состояние MC. Прежний профиль не редактируется; временный удаляется после возврата. Если MC был выключен, созданный стендом процесс останавливается по подтверждённому PID и признаку владения. Ошибка восстановления блокирует новые сессии; исправьте причину и нажмите «Повторить восстановление».

После перезапуска контейнера незавершённое испытание помечается прерванным и выполняется восстановление. Испытание и эмуляция автоматически не продолжаются.

Если безопасный запас диска не подтверждается при восстановлении, MC остаётся остановленным. Возобновление записи блокируется до устранения причины и успешного повтора восстановления.

Перед записью проверяется консервативный логический запас не менее 4 ГБ, во время испытания — 2 ГБ. Резерв журнала учитывается, скидка на экспорты не используется. При исчерпании запаса, резерва тома, перегреве или нехватке памяти нагрузка прекращается. Пороги очистки не меняются. Автоматическое удаление прежнего архива не является сценарием обычного прогона.

## Эмуляция и физические линии

Эмуляция управляет только своими приёмниками и линиями; профиль RJD меняется оператором в обычном интерфейсе. После остановки эмуляции эти настройки сохраняются. Авто-ACK по умолчанию выключен. В интерфейсе отображаются адреса для подключения шлюза, счётчики и кольцевая трасса.

- Программный CAN: отдельный vcan на хосте, удаляемый после закрытия SSH-сеанса.
- Программный Modbus: PTY на хосте. Его `/dev/pts` должен быть виден существующему контейнеру `message-gateway`; иначе проверка недоступна.
- Физический CAN: два разных интерфейса для эмулятора и шлюза, соединённых реальной линией. Оба должны быть подняты с согласованным bitrate. Один интерфейс на двух сокетах проверяет локальную петлю, а не провод.
- Физический Modbus: два разных последовательных порта для мастера стенда и ведомого шлюза. Укажите оба порта и подключите RS485-линию. Наличие порта само по себе не означает успешного физического обмена.
- WS-приёмник по умолчанию слушает `8785/ws/frames`, чтобы не занимать порт signaling-server `8765`. Доступны обычный приём, задержка чтения и периодический обрыв.

Недоступные условия и программные линии не засчитываются как успешная проверка физического обмена.

## Эталонные сценарии

В разделе «Эталоны» создайте сценарий: камера, совместимая конфигурация, SHA256 модели, длительность и независимые ожидания. Загрузите видео размером до 2 ГБ. Камера должна участвовать в слоте техзрения. Готовых размеченных роликов в репозитории нет.

Каждое ожидание содержит `channel`, `start`/`end` в секундах от RTSP PLAY, `minimum`/`maximum` числа совпадений и `fields`. Поля могут содержать вложенный путь, например `dets.0.cls`. Для сквозного зачёта нужны ожидания журнала и хотя бы одного внешнего протокола.

Примеры полей:

| Канал | Поля |
| --- | --- |
| `journal` | `class_name`, `class_id`, `zone.id`, `camera_id`, `config_id` |
| `ws` | `cam`, `dets.0.cls`, `dets.0.cid`, `img.format` |
| `modbus` | `code`, `zone`, `mask`, `count` |
| `can` | `count`, `type`, `danger`, `camera_no`, `padding` |

Modbus сопоставляется с ID новых обнаружений журнала, WS — с камерой и временным окном, CAN — с агрегированными полями и окном. CAN не содержит ID обнаружения. Для RSM и Искры видео воспроизводится отдельными проходами. Если трасса переполнилась до сверки, успешный результат не выставляется. Отсутствие видео или несовместимая модель оставляют сценарий недоступным.

Временные окна относятся к наблюдению стендом: журнал опрашивается каждые 500 мс плюс задержка API, внешние кадры получают время приёма. Смещённые часы шлюза сохраняются как исходные поля, но не используются как часы стенда. Ожидания должны учитывать задержку всей цепочки; кадровая точность времени обнаружения не заявляется. Во время эталона отдельно проверяются работа слотов и ненулевой FPS.

Сегменты испытания выбираются по контрольным номерам индекса, включая открытые на старте файлы. Пакетные дыры и границы внутри сессии MC проверяются по PTS и монотонному времени. Ожидаемая пауза требует совпадения конкретных файлов с контрольными снимками до/после действия и ограничивается его наблюдавшейся длительностью. Между перезапусками MC проверяются число сессий, покрытие потоков и восстановление; точный межсессионный разрыв в кадрах не измеряется.

## Отчёты и API

Отчёты содержат ожидаемый/фактический результат, события, метрики, ссылки и SHA256 доказательств, состояние восстановления. Доступны HTML и JSON. История и эталоны удаляются только вручную; активный отчёт удалить нельзя. Трассы ограничены настройкой объёма и ведут счётчики за всю сессию.

API защищён той же сессией оператора или заголовком `Authorization: Bearer <TEST_PASSWORD>`. Описание маршрутов — `/docs` после входа. Основные маршруты:

- `POST /api/preflight` — условия для заданного `RunOptions`;
- `POST /api/sessions/tests` — запуск выбранных проверок;
- `POST /api/sessions/emulation` — постоянная эмуляция;
- `POST /api/sessions/stop` — остановка с восстановлением;
- `POST /api/recovery` — повтор восстановления;
- `GET /api/state`, `GET /api/events` — состояние и SSE;
- `GET /api/runs`, `/api/scenarios` — история и библиотека.

`POST /api/target/key` и `POST /api/scenarios/{id}/video` принимают бинарное тело с `Content-Type: application/octet-stream`. Загрузка потоковая: проверка диска выполняется до записи данных, затем повторяется во время загрузки. Multipart-обёртка не используется.

## Локальные проверки сервиса

Эти короткие проверки используют временные данные и имитацию целевого API; часовой прогон приложения они не запускают:

```sh
docker run --rm --entrypoint python varan/testing:latest checks/service-check.py
docker run --rm --entrypoint python varan/testing:latest checks/media-check.py
```
