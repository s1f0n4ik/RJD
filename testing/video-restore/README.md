# video-restore

Восстановление минутных mp4-сегментов, у которых не дописан `moov`, и склейка их
в ролики длиной до 20 минут.

Писался под выгрузку регистратора: каталог с подпапками на камеру, внутри файлы
вида `camera_1_2026-07-08_14-16-47.mp4`, HEVC `hvc1`, 25 fps, без звука.

## Требования

Python 3.9+ и ffmpeg/ffprobe. Ищутся в `PATH`, затем в `%FFMPEG_DIR%`, затем в
`C:\Program Files\Ffmpeg\bin`.

## Что бывает с файлами

Регистратор пишет `ftyp / free / mdat / moov`, причём `moov` дописывается
последним. Если запись оборвалась, встречается три поломки:

| verdict | что случилось | лечится |
|---|---|---|
| `mdat_open` | длина `mdat` осталась нулевой, `moov` не записан | полностью |
| `atom_overrun` | `mdat` объявляет больше байт, чем есть в файле | с потерей хвоста |
| `empty` | 0 байт | нет |

Внутри `mdat` лежат NAL-юниты с 4-байтным префиксом длины, и первыми тремя идут
VPS/SPS/PPS. Поэтому файл самодостаточен: донор для восстановления не нужен.

## Команды

Каждая команда без `--apply` только печатает план и ничего не трогает.

```
python restore.py scan      E:\06.08.2026
python restore.py repair    E:\06.08.2026 [--apply] [--jobs 4]
python restore.py merge     E:\06.08.2026 [--apply] [--jobs 1] [--out D:\merged]
python restore.py verify    E:\06.08.2026 [--out D:\merged]
python restore.py clean-bak E:\06.08.2026 [--apply]
```

### scan

Обходит верхнеуровневые атомы, читая только заголовки, и берёт длительность из
`mvhd`. Кладёт разбор в `restore-state.json` в корне. Остальные фазы сканируют
сами, файл состояния нужен для отчёта, а не как кэш.

### repair

На каждый битый файл: идёт по цепочке NAL, обрывается на первом, чья длина
выходит за конец файла, пишет Annex-B во временный каталог и ремуксит

```
ffmpeg -r 25 -f hevc -i tmp.h265 -c copy -tag:v hvc1 -video_track_timescale 2500
```

`-tag:v hvc1` обязателен: из сырого потока ffmpeg по умолчанию ставит `hev1`, а
исходники размечены как `hvc1`, и склейка потоковым копированием требует
одинакового тега.

Результат прогоняется полным декодом `ffmpeg -v error -i … -f null -`. Любой
вывод в stderr означает, что ремонт не принят.

- принят — оригинал уезжает в `<имя>.mp4.bak`, починенный встаёт на его место;
- данных нет вовсе (0 байт, ни одного целого NAL, ноль кадров после ремукса) —
  файл удаляется;
- отработал сам ffmpeg с ошибкой — помечается `failed` и **не** удаляется,
  разбирается руками.

Временные файлы пишутся в системный temp, а не рядом с исходниками: если
исходники на медленном внешнем диске, лишние проходы головкой ни к чему.
Переопределяется через `--tmp`.

### merge

Внутри камеры сегменты сортируются по метке времени в имени. Группа закрывается,
когда суммарная длительность видео дошла бы до 20 минут, либо когда до
следующего сегмента разрыв больше 90 секунд — так ни один ролик не перескакивает
через паузу в записи.

Склейка потоковым копированием:

```
ffmpeg -f concat -safe 0 -i list.txt -c copy -tag:v hvc1 -f mp4
```

`-f mp4` нужен потому, что пишется во временный `.part`, и по расширению муксер
не определяется.

Результат проверяется через ffprobe: длительность должна сойтись с суммой
исходных в пределах 2 секунд, иначе файл удаляется и группа помечается `failed`.
Готовые ролики при повторном запуске пропускаются, так что прогон можно прервать
и продолжить.

Битые файлы, если `repair` не запускался, пропускаются с предупреждением и
перечисляются в sidecar.

Раскладка вывода — `<root>\merged\<камера>\`, рядом с каждым роликом `.txt` со
списком исходных сегментов, их смещениями и настенным временем:

```
camera:     camera_1
start:      2026-07-08 14:16:47
segments:   6
expected_s: 266.066
actual_s:   266.066

  offset_s  wall_clock             dur_s  source
     0.000  2026-07-08 14:16:47   23.960  camera_1_2026-07-08_14-16-47.mp4
    23.960  2026-07-08 14:17:07    4.080  camera_1_2026-07-08_14-17-07.mp4
```

`--jobs` для merge по умолчанию 1. Если чтение и запись идут на один физический
HDD, параллельные процессы только гоняют головку и делают хуже.

### verify

Сверяет каждую склейку с её исходниками покадрово: берёт число кадров из `stsz`
и там, и там, и сравнивает. Заодно проверяет, что каждый исходный сегмент вошёл
ровно в одну склейку и ни один не потерялся. Всё чтение — свой разбор атомов, ни
одного запуска ffprobe и никакого декодирования, так что 19 тысяч файлов
проходят за минуты. Возвращает 1, если нашлось хоть одно расхождение.

Это надёжнее, чем `ffmpeg -f null`, которым проверяется ремонт. На склейке
`-f null` даёт ложные срабатывания «non monotonically increasing dts to muxer»:
у части камер `avg_frame_rate` дробный (например `1843750/73777`), ffmpeg на
выходе округляет метки времени в этот таймбейс и периодически схлопывает две
соседние в одно целое. В самом mp4 при этом PTS и DTS строго монотонны, а число
кадров сходится точно.

### Известное поведение на стыках

Починенный сегмент с обрезанным хвостом может потерять при склейке свой
последний кадр: демуксер concat отбрасывает его независимо от позиции сегмента,
и `-fflags +genpts`, `-copyts`, `-avoid_negative_ts` на это не влияют. Речь идёт
о кадре, на котором регистратор и оборвал запись.

На прогоне 06.08.2026 это дало ровно 1 потерянный кадр на 27 171 686: 99 из 100
починенных сегментов склеились кадр-в-кадр.

### clean-bak

Удаляет `.mp4.bak` там, где рядом лежит исправный `.mp4`. Отдельная команда,
чтобы резервные копии жили до тех пор, пока результат не устроит.

## Границы

Скрипт не удаляет и не перезаписывает целые файлы. Единственная перезапись —
битый файл своей починенной версией, с `.bak` рядом. Единственное удаление —
файл, из которого не извлеклось ни одного кадра.
